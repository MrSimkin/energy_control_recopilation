# Solar of Things Windows App — Initial User Requirements

Date: 2026-09-24

Status: INITIAL REQUIREMENTS — USER-STATED / NOT YET FINALIZED

## 1. Project goal

Build a Windows desktop application/software, with ChatGPT guiding the user as the final user/product owner, that connects to Solar of Things / SiSeLi cloud services and retrieves the data needed to produce energy statistics and reports.

The implementation architecture is not yet selected.

Mandatory constraints:

- Windows application/software.
- Zero monetary cost for the software stack and required services.
- Must **not** be implemented in Java.
- The application must be in English.
- It must use the cloud/API path established by the Solar of Things research already stored in this repository.
- Local/BLE/MQTT-interception/device-control branches remain out of scope unless the project scope is later changed.

## 2. Data philosophy

The application must preserve data as purely/rawly as practical as it comes from Solar of Things, while also processing/normalizing it as needed for the reporting and statistical scope.

The design must preserve enough raw source information to:

- audit calculations;
- change normalization rules later;
- recover from model/protocol differences;
- avoid losing source values when producing processed statistics.

## 3. Time-period selection

The user must be able to select data by at least:

- day;
- week;
- month;
- X number of months;
- range of months;
- year;
- moving/rolling year;
- year to date;
- arbitrary date range.

## 4. Aggregation/granularity

Independent of the selected date range, and when the selected range makes the granularity meaningful, data must be aggregatable for tables and graphs by:

- hour;
- day;
- week;
- month;
- year.

## 5. Required energy/statistical data

At minimum, the application must support or derive the following when the Solar of Things data available for the target inverter allows it:

1. Power generated by the solar panels.
2. Power used by the house that comes directly from solar panels.
3. Power used by the house that comes directly from the battery.
4. Power used by the house that comes directly from the power grid.
5. Energy stored in the battery:
   - percentage (%);
   - W / appropriate power-or-energy representation, to be clarified during design.
6. Total energy consumption of the house.
7. Rate of energy consumption of the house.

Additional data may be added after design discussion if it materially improves usefulness, validation, or interpretability.

## 6. Presentation

The user must be able to choose:

- which data/metrics to display;
- the presentation form:
  - table;
  - summary;
  - graph;
  - combinations of these.

Graphs must be dynamic/interactive.

Multi-axis graphs should be supported when useful and technically appropriate.

## 7. Saved report preferences

The user must be able to save display/report preferences as reusable preset reports.

A preset should be able to preserve, at minimum:

- selected metrics;
- presentation type(s);
- relevant chart/table configuration;
- aggregation/granularity;
- other report options later defined during design.

Date ranges may be fixed or relative depending on the report design; this remains to be decided.

## 8. Export

All reports must be exportable in a clear and readable format.

Exact export formats are not yet selected and will be decided during design.

## 9. Electricity-utility monthly readings

The application must allow manual entry of the electricity-consumption reading/value stated by the electricity utility/company for power taken from the grid.

Characteristics:

- approximately one reading/value per month;
- must be stored locally;
- must be available as another data series/metric in reports;
- must be comparable with Solar of Things / SiSeLi-derived grid-consumption data.

The exact meaning of the utility value — monthly consumption, cumulative meter reading, billed consumption, billing-period consumption, or another field — must be clarified before implementation.

## 10. Target hardware context

Known target inverter:

- user description: **SPRO-6200**;
- 230 V class;
- nominal 48 V battery system;
- Solar of Things cloud monitoring.

Research currently identifies a strong public-family match to a SUNPRO/SPRO Energy 6.2 kW / 48 V / 220–230 V hybrid inverter, but the exact SiSeLi model/protocol is intentionally not hard-coded.

The future application must perform local read-only device/schema self-discovery after login, as defined in the completed API research.

## 11. Existing research authority

The completed research under:

`solar_of_things_api_research/`

is the technical evidence base for the application.

Important inherited design constraints include:

- dynamic device/schema discovery;
- raw-source preservation;
- IDs stored losslessly as strings;
- timezone-aware history;
- pagination/backfill;
- null/missing values distinct from measured zero;
- per-device field/unit/sign normalization;
- validated server aggregates where appropriate;
- read-only cloud acquisition;
- token refresh single-flight;
- no assumption of a fixed universal inverter field dictionary.

## 12. Open design questions

These initial requirements are intentionally not final.

Topics still requiring discussion include:

- feasibility of each requested metric;
- exact meaning of “battery energy stored in W”;
- exact meaning of “rate of consumption”;
- how to calculate source contribution to house consumption (solar vs battery vs grid) when the API does not directly expose all flows;
- preferred report/export formats;
- relative versus fixed saved report periods;
- electricity-utility reading semantics;
- architecture, language/framework and local database;
- whether additional validation/quality metrics should be visible to the user;
- whether cost/savings and grid-import/export statistics should be included.
